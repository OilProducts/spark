Runs tab: audit and redesign

September 28, 2026. I read frontend/src/features/runs and the transcript projection in attractor-runtime, then drove the live app (read-only) on run-18d93c056079b9c0 (CR-2026-0127). That run executed Implement 4×, Evaluate 4× and Validate 2×, and spawned 4 child runs. The mockups below use that run's real data.

1. Why repeated nodes break the Activity tab

This is not one bug. Five defects stack, and together they make a looping run unreadable. An execution (node + visit) is not a first-class identity anywhere in the runs UI.

  1. Every execution writes the same turn id. The per-execution transcript projection hard-codes "turn_id": "response" (crates/attractor-runtime/src/handlers.rs:123, :1176). Segment ids are event-<local sequence> and final-response, which are unique only within one execution. In this run, 160 segments from 12 executions share one turn id, and 15 segment ids collide.
  2. The frontend groups by turn id. buildRunTranscriptGroups keys groups on segment.turn_id (model/transcriptModel.ts:99), so the whole run collapses into one group. That group is labelled with whichever node came first, and rows from different executions are interleaved by their per-execution order. In the live app this run shows a single header, RESULT_SUMMARY, over 887 elements.
  3. The visit is dropped on the way in. fetchExecutionSegments (lib/api/attractorApi.ts:1155) knows stage_index but stamps only attempt. That is the retry count, which is 0 for every loop revisit. Even a corrected label could not say "Evaluate, visit 3".
  4. Two sequence spaces are sorted together. latest_sequence on a segment is the execution-local event number (up to ~541). Activity sorts it against root-journal sequences (1–70) (RunActivityCard.tsx:215), so the transcript blob lands after PipelineCompleted, and the transcript/event interleaving is meaningless.
  5. Colliding ids overwrite each other. Live applySegmentUpsert dedupes on segment.id (state/runTranscriptStore.ts:63), so final-response or event-25 from visit 2 replaces the one from visit 1. React keys collide in the same way.

Surrounding symptoms:

  • Focusing Implement shows none of its 4 child runs' transcripts, because child segments carry child node ids (work).
  • The graph keeps one status per node, and the last write wins. Evaluate shows green although it sent the work back twice, and nothing shows a node ran 4×.
  • Events label visits with the internal (index 11).
  • A review that requests changes (failure_kind: business, routed on the Fix edge) renders as "Stage failed · ERROR · stage_failed". A normal, designed loop looks like a crash.

Prerequisite for every proposal: carry (run_id, node_id, stage_index, attempt) on every segment and event. Make that tuple the group key and a globally unique id prefix, and give each execution an outcome that distinguishes routed from failed. Most of this can come from the executions list the status endpoint already returns. The rest is the two backend id literals above.

3. Proposals

All four are clickable. Try selecting executions, the visit pickers, and the keyboard shortcuts noted on each page.

A · Execution ledger

The run as an ordered list of executions grouped into passes (Setup, Pass 1–4, Wrap-up). Each visit is its own row with its outcome, summary, child run and duration. A detail pane shows that visit's transcript, prompt and response, with a visit switcher (1 2 3 4) and ←/→ between visits. A flow strip marks ×4 and ↺2 on the nodes that looped.

+ Fixes the repeated-node problem structurally. Scales to long runs. Cheap: a list plus a pane, and it reuses the transcript rows.

− Parallel branches need an indent treatment. It shows less of the flow's shape than the graph does.

B · Trace

A profiler-style timeline with one lane per node and one bar per execution. Colour shows outcome, and child runs appear as nested spans. Pass boundaries are marked. A side panel shows where the time went and a loop summary. Clicking a bar opens that execution.

+ Duration, parallelism and loops can be read at a glance. It is the only view that answers "why was this slow".

− Short steps become slivers. A timeline is a weaker reading surface than a list. Zoom and pan need building.

C · Graph replay

The graph becomes the page. Nodes carry visit badges and "ran 3× · last: succeeded". Edges carry traversal counts (×3 on Implement→Evaluate). A bottom scrubber steps or plays through the 18 executions and lights up the node and the edge just taken.

+ The most intuitive picture of how a loop happened. It reuses the existing graph investment and suits "Continue from this step".

− It inherits the graph-layout problems (G02). A scrubber with hundreds of steps gets dense. It is the most expensive option.

D · Inbox + run report

Runs home is an inbox with Needs you / Running / Failed cards over a searchable table titled by objective. A run page reads like a PR description: outcome facts, a short "What happened" account per pass, review findings with the pass that fixed each one, and evidence chips that open each execution. (inbox view)

+ Best for "did it work and why" and for people who didn't watch the run. It pairs naturally with Missions.

− The narrative needs a summarizer, or at least per-execution notes and review summaries. It is weak for watching a live run.

4. Combined proposal

E · Visit list + graph (A + C + D's header)

A flat list of every node execution, each labelled “visit n of x”, with no grouping. The graph sits beside it and shows visit counts on nodes and traversal counts on edges; the edge into the selected visit is highlighted. The detail pane has a visit picker plus from/next links, so you can follow the route either way. Clicking a node filters the list to its visits. “As of selected visit” and Replay turn the graph into C's replay. D's report header sits on top with outcome facts, the result, and review findings that link to the visit that fixed each one. The runs list is a drawer (r) and the graph can be hidden (g).

F · E, quieter

Same model as E, with the noise removed. Each fact is shown once. Colour appears only on visits that were sent back or failed. List rows are one line (name, n/x, duration). The graph has no captions and labels only its loop edges (“back ×2”). The result and review findings are the first item in the list instead of a header bar. Each visit is a single transcript (instructions and reads, the work, then what it returned and wrote). Context is a list item with per-key history. There is no Artifacts tab.

4b. F against other flows

Open F, generalized → This is the frozen F layout, driven by generic/extract.py from six real run records (current log format only; older history is being wiped). The runs:

  • the implement-change baseline;
  • a math resolution-program run that failed when its container wouldn't start;
  • an implement-spec run that failed after 66 stages and 17h when the backend dropped;
  • a tool-heavy merge-change;
  • an Implement Task child replayed while waiting on a question;
  • a child run opened on its own.

Nothing in the renderer is specific to one flow. The four design languages can be applied to it.

What held up:

  • The visit model: n/x, instructions and reads, the work, and what it returned.
  • The status item first: Result, Failure or Question.
  • Context as a list item.
  • The generated “Didn’t pass” list, which explains failure-driven loops for any flow.

What the real data exposed:

  • No generic reason for a business failure. A rejected review records stage_failed, and the reason lives in a flow-specific key. The page can only say “no reason recorded · wrote review.summary”. The runtime should carry the agent's notes on failure, as it does on success.
  • Not every loop is a failure. In resolution-program, every Review succeeds and still routes back to Resolve five times. The list shows nothing unusual. Only the graph (“back ×5”) and each visit's “next … via …” line explain it. A loop-back should be marked in the list whatever its outcome.
  • Interrupted visits. Long runs contain visits that started and never finished. They now read “Interrupted” once the run is over, instead of looking live.
  • Titles. The first filled-in launch input gives “README.md” (implement-spec), a branch name (merge-change), a request path (implement-change) and a paragraph (math). Child runs borrow the parent's title. A flow-declared title input is needed, and it's a prerequisite for the title-first looks.
  • Results can be the wrong output when a flow's result is set to a node's raw output. The page now labels the result's source.
  • Runs can be started by triggers. The header says so.
  • Parallel branches are supported by the renderer, from the ParallelBranch* events, but none of the current-format runs on disk uses them, so that path hasn't been checked against real data.
  • The auto-laid-out graph is legible at 18 nodes but crowded with back edges. It argues for hiding the graph by default and making it wider on demand.

5. Recommendation

  1. Fix execution identity first (section 1). This is a bug fix and a prerequisite, and the current tab gets usable with it alone.
  2. Ship A (ledger) as the run page's main surface. It is the smallest change that makes loops legible, and it replaces the Activity/Events/Transcript mode switch with one list.
  3. Use D's report header for finished runs: outcome, passes and findings above the ledger. Adopt D's list changes: objective as the title, readable ids, start time, search, and child runs collapsed under their parent.
  4. Add B's trace later as a toggle in the ledger header, for performance questions. Hold C until the graph layout issues are fixed.
