---
title: Software change
description: Design a change, challenge the proposal, implement it, independently verify the result, and deliver it within the mission's authority.
---

Take a requested repository change from intent to a verified result. The mission's objective defines the outcome, constraints, and delivery authority.

1. Design: launch `software-development/design-change` with the requested outcome as `context.request.objective` and the relevant constraints. Ground the proposal in the actual code and existing mechanisms.
2. Evaluate the proposal yourself against the objective and repository. Resolve material open questions before implementation. Simplify wherever a smaller solution meets the requirement; generalize only when actual consumers need shared behavior. Cut speculative scope and return the proposal for revision when needed.
3. Implement: launch `software-development/implement-change` with the evaluated proposal as either `context.request.objective` or `context.request.artifact_path`, plus the acceptance criteria, constraints, and the project's validation command. Let the flow implement, independently evaluate, and validate the change in its isolated worktree.
4. Verify the result: launch `software-development/review-change` with the resulting branch or commit as `context.request.source_ref`. Evaluate the work yourself too: inspect the actual diff, trace the behavior through its real callers and boundaries, and check the validation evidence. Prove the intended outcome at the boundary users observe; for UI changes, exercise the integrated app. Where the change spans integrations or platforms, verify the relevant ones and state their actual limits. Fix material defects, then recheck the changed behavior and outstanding findings.
5. Deliver to the destination authorized by the objective. When merging is authorized, launch `software-development/merge-change` with the verified branch or commit as `context.request.source_ref`; check the resulting commit and validation of any changed integration tree. Push when authorized, using the project's intended remote and branch. If delivery goes through a pull request, address required checks and verified review findings on its latest commit before merging. If the objective ends at a reviewed branch or proposal, hand that over instead. This playbook grants no delivery authority beyond the user's request.
6. Close the mission with the outcome, final commits and delivery destination, proof, and any remaining limitations. Confirm the requested delivery actually completed before declaring success.

These are guidelines, not a script. Skip a step only when existing evidence already covers its purpose, and return to design when implementation or review disproves the approach. Before accepting a run's claims or choosing the next step, read its record and the commits or artifacts it names; consult logs when needed. Check findings yourself: make the smallest justified fix or reject the finding with evidence. Keep independent review separate from authorship, resist scope growth, and do not count an exhausted review budget or missing response as approval. Ask the user only for missing decisions or authority; an earlier authorization remains valid. Keep the audit trail in the mission and its runs rather than creating duplicate reports.
