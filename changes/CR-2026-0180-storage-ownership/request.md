# Spark storage by ownership

## Problem

Spark separates storage by subsystem rather than ownership. Project behavior is partly shareable files and partly installation records; private state is partly global and partly in the checkout. The operator wants IDE-like project configuration that travels with a checkout, with this installation's history, credentials and learned memory kept separately.

This design supersedes the proposed placement in [CR-2026-0179](../CR-2026-0179-storage-placement/request.md), not its useful inventory. Moving trigger definitions out of the project would contradict the requested direction. That proposal also retained stores with no current writers and missed the existing project model-default authority.

Evidence below was checked at `7409b8c18a00093152c3f1d8e533775bb3bacf7f` (the current HEAD). References name existing files and symbols; proposed paths and symbols are explicitly described as new. No disk-size or performance measurements were made. This is an ownership and duplicate-authority change, not a measured performance optimization.

Verified starting points:

- [project.rs](../../crates/spark-common/src/project.rs), `definitions_dir` and `state_dir`, separates authored definitions from local working state, but this repository's [.gitignore](../../.gitignore) ignores all `.spark/`. Its definitions documentation still lists obsolete categories.
- [storage settings](../../crates/spark-storage/src/settings.rs), `read_project_model_defaults`, reads `[model_settings]` from registry `project.toml`. [workspace settings](../../crates/spark-workspace/src/settings.rs) writes that same authority. Project model defaults already exist; a project-stored settings document does not.
- [workspace_projects.rs](../../crates/spark-storage/src/workspace_projects.rs), `ProjectRecord` and `ProjectRegistry`, also stores execution-profile choice there, alongside private favorites and active-conversation state.
- [attractor API](../../crates/attractor-api/src/lib.rs), `NodeOverride` and `apply_node_overrides`, already supports launch-time per-node model choices. `PipelineStartRequest` distinguishes owning `project_path` from execution `working_directory`, but `start_pipeline` currently reads model defaults using the latter. Worktree execution can therefore select the wrong project's defaults.
- [trigger storage](../../crates/spark-storage/src/workspace_triggers.rs), `TriggerRuntimeStateRepository::load`, treats missing or malformed state as the enabled default. `TriggerDefinitionRepository::list` silently skips individual invalid definitions. Definition presence, activation and read failure need distinct meanings.

## Goals and non-goals

Goals:

- Make authored project behavior editable, portable and normally committable through definitions in `<project>/.spark/definitions/`. Model choices that differ by flow or node are written into a project copy of the flow, which replaces its bundled counterpart.
- Keep one authority for each value. Consolidate structured private records in the existing SQLite mechanism; retain directly consumed content as files.
- Require explicit installation activation of project triggers; deletion and corruption must never cause implicit activation.
- Remove demonstrated duplicate or obsolete stores, while preserving useful run evidence, agent-editable memory, uncommitted work, containment checks, revision conflicts and failure recovery.

Non-goals: a project `settings.toml`, any replacement settings mechanism, a separate flow/node override layer, changes to existing launch-time model selection precedence; migrations, automatic imports, compatibility readers, automatic historical-directory purges, new dependencies or generic persistence/patch frameworks; changing default `SPARK_HOME`; checkout-relocation identity, shared history across clones, multi-root workspaces, backup services, redesigning native tools' internal homes, independently placing child runs, or moving change requests. No project-specific context keys in shared code. This document authorizes implementation changes to the storage contract, including the authoring guide's current rule that all working files live in project state; implementation must update that rule and its consumers together.

## Approach

Let `P = <project>/.spark/`, `H = SPARK_HOME` (default `$HOME/.spark`), and `G = H/projects/<project-id>/`. Keep normalized-path identity from `build_project_id` in [project.rs](../../crates/spark-common/src/project.rs). A checkout at another path gets another installation identity; it does not inherit private history merely because its files match.

The resulting layout is:

```text
P/
  definitions/{flows,roles,playbooks,triggers}/
H/
  config/spark.toml
  config/clients/<client-id>.toml
  config/provider.env                 # operator-managed
  state.sqlite3                       # SQLite-managed sidecars alongside
  server.lock
  projects/<project-id>/
    conversations/<conversation-id>/  # referenced blobs and optional traces
    memory/<role>/                    # agent-editable Markdown
    runs/<run-id>/                    # execution record and content
    work/                             # durable private working files
  runtime/{codex,claude}/
  bundled/{flows,roles,playbooks,guides}/
```

Temporary replacement/deletion files are allowed beside project destinations. They are not durable working directories. Installation-wide settings remain authored TOML; existing private project defaults move with registry rows into SQLite. No second run index is added.

### Project definitions and private defaults

Do not create `<project>/.spark/settings.toml`. There are no project-file `[models]`, `execution_profile_id` or `[flows...]` sections and no replacement settings mechanism. Per-flow/per-node model choices belong directly in a project copy of the workflow under `P/definitions/flows/`, using existing authored selection fields. Project definitions replace bundled definitions of the same name through the existing project-first resolver; no additional override or precedence layer is introduced.

Coordinator assumption (not an operator decision): preserve the existing project model-default and execution-profile controls as installation-private features. Move their current registry `project.toml` `[model_settings]` and `execution_profile_id` values into SQLite with the rest of the project registry. Existing API/UI controls read/write those rows, preserving validation, repair responses, expected-revision conflicts and profile-reference serialization. Model defaults still use the existing whole-selection `ModelSettings` semantics. Installation defaults, private project defaults, authored selections and explicit launch selections retain their existing resolution behavior. Execution-profile selection retains the existing installation/project/explicit-launch precedence and missing/disabled-profile errors; it gains no flow-specific setting. There is no import from old registry files.

Fix the verified owning-project lookup in `start_pipeline`: when `project_path` is supplied, load private project defaults for that owning project rather than the worktree `working_directory`. With no supplied project, retain the normalized working-directory fallback and bundled-only flow resolution. Preserve existing launch-time `NodeOverride`, validation and shared-session checks; do not move its DTO or introduce new merge rules for an override layer that no longer exists.

Children keep their existing runner and inherited placement, including copied execution-profile and lock state in [manager_loop.rs](../../crates/attractor-runtime/src/manager_loop.rs), `launch_default_child_run`. No project flow/node settings resolver, child override resolution/snapshotting, child profile-compatibility check, or extraction of the execution-profile selector into `spark-common` is needed. Existing run configuration capture/resume behavior remains. Execution locks remain repository-scoped serialization independent of profile selection: [FlowExecutionLock](../../crates/attractor-core/src/flow_definition.rs) contains only scope, key and conflict policy. Preserve existing queue/acquire/release and parent/child inheritance behavior. Independently placed children remain out of scope.

### Installation configuration and private transactions

Combine core settings and profiles in `H/config/spark.toml`: existing core sections remain; use `[llm_profiles.<name>]`, `[execution_profiles.<name>]` and `[execution_defaults]` (`execution_profile_id`) to avoid the two old documents' competing `[profiles]` namespaces. Pass these sections to existing parsers; update every profile loader, reference validator, API diagnostic and settings editor together. No reads of the former files. One document revision/lock serializes section updates, preserving unrelated sections. Retain the profile-reference serialization boundary when checking/writing references, consistently before document locks; launch resolves a coherent configuration snapshot. Credentials and host/container connection details stay installation-owned.

Expand the existing SQLite database, rather than implementing another persistence layer. Add project registry rows (unique normalized path and project ID), standing-role and mission rows (project + record ID), trigger activation rows (project + definition ID), milestones (unique milestone ID, ordered sequence), and per-run projection progress. Preserve existing record payload fields/validation and optimistic revisions; JSON payload columns are sufficient for unqueried fields. Use concrete tables/repository methods, not a generic entity framework. Role/mission read-modify-write and trigger schedule/delivery claims run in immediate transactions, replacing per-file locks without losing concurrent updates. Preserve conversation revision/tombstone/deletion semantics and existing project lifecycle admission/cleanup gates. Emit live notifications only after successful commit; retries must not publish rolled-back changes.

Project milestones and projection progress commit together, with uniqueness on the existing deterministic milestone identity. Preserve ordering, tail limits and live API shapes. A crash/retry cannot duplicate a milestone or advance progress without it. Do not derive a second run catalog from these rows: run files remain the authority and run enumeration reads their roots.

Retain the server process lock. SQLite transaction locks replace structured-record locks only; they cannot replace filesystem revision/atomic-write boundaries for authored TOML. Database corruption is an error, never a reason to synthesize armed automation or silently discard records.

### Trigger lifecycle

A project definition makes a trigger available. Activation is an explicit installation action after validating effective profiles and targets. UI create with `enabled=true` may save the definition and activate as that one user action; externally added/cloned definitions start inactive. Save definition first; activation failure leaves an available inactive definition with a reported error. No credential may enter shared TOML. Mission IDs and other installation-local targets are required private activation bindings, validated on activation; missing bindings prevent activation and firing. Portable names resolve in the owning project.

Missing activation means inactive; malformed private state is an error. Reconciliation must enumerate supported definition filenames independently of parsing, distinguishing a successful absence from unreadable/invalid content. Report an invalid definition and prevent its execution; do not interpret it as deletion or let it disappear silently. An unavailable project/permission failure is not proof that all its definitions were removed.

On confirmed definition removal, immediately make new dispatch impossible and delete activation/credentials/deduplication state during reconciliation. The scheduler, webhook handler and manual fire path must recheck a readable present definition and active matching state at dispatch, not rely only on a cached list. API deletion clears activation immediately even if later file cleanup fails; a definition left on disk remains inactive. Changes to source/action/profile inputs invalidate activation until explicitly revalidated; retain a fingerprint, not a second definition authority. Descriptive edits need not disarm.

Recreating a definition after observed deletion does not restore credentials or activation. Reconciliation runs at startup and before accepting new activation/dispatch, and scans registered projects. Deletion/recreation that occurs entirely between observations with identical bytes is inherently unobservable; it is treated as the unchanged definition. No filesystem watcher or historical identity service is added to promise otherwise. An already dispatched execution may finish; removal prevents new dispatch, not rollback of external actions. Keep delivery deduplication/claims transactional and preserve current retry behavior; do not claim exactly-once external side effects.

### Private paths, run files and project staging

Use one shared calculation for `G` and its private file roots. Default run resolution changes to `G/runs/<run-id>`; an explicitly configured external runs root retains `<configured-root>/<project-id>/<run-id>`. Update enumeration, resume, artifacts, deletion and container workers together; do not scatter default-path tests through callers. External native runtime overrides remain supported. Reads do not create/register projects merely to compute a path.

Provide new generic runtime context binding `internal.project_work_dir` and shell environment `SPARK_PROJECT_WORK_DIR`, both naming `G/work`. Supply the same path in conversation/standing-role agent instructions as well as flow tasks. These are runtime-owned bindings, not user launch-context inputs. Each flow selects its own subtree. Root and child runs use the root owning project's work area even when their execution directories differ. Capture the binding with execution configuration. For local containers, bind the work root read/write at the same absolute path (and memory when the task uses it), using the existing [container mount mechanism](../../crates/attractor-execution/src/container.rs); reject conflicting mounts or unavailable paths before execution. Preserve configured remote execution mapping requirements and fail explicitly when a profile cannot expose the bound paths. Never silently send host-only paths to agents.

Replace bundled `.spark/state` writers and readers together, including spec ledgers/validation/symlink references and Chief of Staff proposals. Update [flow authoring](../../crates/spark-assets/assets/guides/flow-definition-authoring.md) and [operations](../../crates/spark-assets/assets/guides/spark-operations.md) to the new contract. Worktrees still depend on the source Git repository; global placement does not make them independently movable. Do not move or remove existing worktrees automatically.

Memory stays in `G/memory/<role>/`, separately from work and records. Use the same settings-aware `memory_dir` for generated role instructions and the memory API. Preserve role/relative-path validation and canonical containment: memory directory must stay within canonical `G`; each requested file must stay within its canonical role-memory directory. Preserve empty listing/not-found behavior for missing memory and reject escaping symlinks. Do not broaden the allowed boundary to all of `H`.

Keep project definition atomic staging on the destination filesystem: same-parent `.spark-storage-*` files, and reserved `.spark-deleting-*` staging beside the definition directory for directory deletion. Preserve current symlink rejection and recoverable failed-deletion evidence from `stage_for_deletion` in [API](../../crates/attractor-api/src/lib.rs). No general durable `P/state` root remains. Definition enumeration must skip reserved staging names. Replace this repository's blanket `.spark/` ignore with rules for old local `state/`, known generated/transient subtrees and reserved temporary/lock names, allowing supported definitions to be added normally. Removing an ignore rule never authorizes adding all existing local `.spark` content to Git.

Run cleanup keeps only `checkpoint.json` and root `manifest.json`. Remove obsolete path methods, checkpoint options, fallback readers and artifact entries in one buildable step. Result persistence omits `body_markdown` from JSON while preserving it in the public `RunResult` assembled from Markdown; a missing required Markdown file is an error, not a compatibility fallback. Keep each file atomically written, metadata written last; do not claim a transaction across two files. Results are materialized at terminal completion as today. Remove empty `run.log`, its unused append helper and artifact/path exposure; actual activity/event evidence stays intact.

### Deletion, reset and Home

Manual filesystem deletion is not Spark's project-removal API. Preserve that API's conversation lifecycle gates, interruption, tombstones, checkpoint-before-cleanup ordering and retryable deletion markers. In the current [conversation store](../../crates/spark-storage/src/conversation/store.rs), `finish_project_deletion_locked` recursively removes only the registry project root, currently `H/workspace/projects/<id>` in [workspace_projects.rs](../../crates/spark-storage/src/workspace_projects.rs). Current memory (`roles::memory_dir` in [roles.rs](../../crates/spark-workspace/src/roles.rs)), worktrees and run roots ([RunRootPaths::new](../../crates/attractor-runtime/src/paths.rs)) lie outside that directory and survive project removal. Relocating them under `G` must preserve those lifetimes, rather than expand deletion to match the new physical boundary.

The project-removal contract is an explicit allowlist:

| Data | Project-removal action |
| --- | --- |
| Registry/UI row; conversations, turns, segments, conversation workflow artifacts, attachment/blob references, conversation runtime sessions and inbox records | Remove/tombstone through the existing conversation deletion protocol, preserving revision and deferred-cleanup guarantees. Conversation runtime sessions here are database records, not the native tool's home or pipeline run files. |
| Standing-role and mission records; trigger activation/bindings, secrets, schedule/delivery state | Remove the project's private rows. Removed activations cannot dispatch new work. Late trigger outcomes must not recreate removed activation rows. |
| `G/conversations/` | The sole project file subtree removed by project-removal cleanup: attachments, full tool outputs and optional conversation traces follow their deleted conversations, after checkpoint/admission checks. |
| `G/memory/`, `G/work/` | Retain unchanged, including learned Markdown, uncommitted worktrees, proposals, ledgers and symlinks. Cleanup must not traverse or follow their symlinks. Targets stored inside these retained trees survive too. |
| `G/runs/` and `<configured-external-runs-root>/<project-id>/` | Retain all pipeline run records, checkpoints, events, captured configuration/definitions, artifacts, logs and results. No active or terminal run is removed by project removal, regardless of the root's location. |
| Global milestones/projection progress; installation settings, native homes and bundled assets | Retain. Milestones describe historical runs and must not cascade-delete with registry rows. |
| Project definitions and arbitrary other project files; unknown siblings under `G` | Retain; they are not cleanup targets. |

Delete only `G/conversations/`, not all children of `G` except a keep-list. Do not rename, traverse, empty or remove retained trees during initial cleanup, retry or startup recovery. Remove `G` itself only with a nonrecursive empty-directory removal; a retained subtree or unknown sibling is successful cleanup, not a reason to keep the deletion marker pending. Remove the database registry row independently of directory existence. Re-registration of the same normalized path can reuse retained memory/work and discover retained run files by their existing path-derived identity; it must not import deleted conversation/role/mission records or reactivate triggers. Starting a standing role again is an explicit action and can reuse its retained memory. Run enumeration/read/resume must continue to work for retained run roots without treating directory presence as registration. No second run index or automatic purge is added.

Project removal interrupts conversation turns through [WorkspaceProjectService::delete_project](../../crates/spark-workspace/src/projects.rs) and [stop_execution](../../crates/spark-workspace/src/conversations.rs), which calls the conversation agent backend. It does not stop or fence pipeline runs: [RunStore](../../crates/attractor-runtime/src/store.rs) writes run records/events/checkpoints independently of the conversation project gate. Already running pipelines may continue using captured configuration and write their retained run/work/memory files after removal. Keep that behavior; do not add pipeline cancellation or a new runtime admission mechanism in this storage change. Their writes must not recreate deleted registry/conversation/activation rows; attempts to append to tombstoned conversations remain rejected. Retained run/milestone data must not require a live registry row or cascade-delete with it.

Correct the [removal dialog](../../frontend/src/features/projects/hooks/useRemoveProject.ts): its current claim that runs are deleted is contradicted by the actual cleanup paths and must not define this contract. The dialog should say removal deletes registration, local conversations and installed automation records, while retaining project files, pipeline run history, learned memory and working files; already running pipelines continue. Assume Spark is stopped for installation resets; deleting live SQLite files is not a reset protocol.

| Deleted data | Consequence |
| --- | --- |
| Project-removal API | Deletes the private rows and `G/conversations/` listed above. Retains memory, work, all default/external pipeline runs, global milestones and project files. Running pipelines continue. A remaining `G` directory is not a registered project. |
| Ordinary project's `P`, separate from `H` | Authored definitions are lost. Bundled fallback still applies to names it supplies; surviving runs do not recreate project files. Private history/memory/work survive. Missing trigger definitions prevent new dispatch; reconciliation removes their activations. |
| Private SQLite state | Registry (including private project model/execution defaults), conversations/structured artifacts, roles/missions, activations/secrets, milestones and bookkeeping are lost. Surviving project definitions never re-arm triggers. Unreferenced blob/run/work files are not automatically imported or purged. |
| `G/work` or memory | May destroy uncommitted work, break resume or lose learned knowledge. These are persistent data, not cache. |
| Whole `H` | Also loses installation configuration, default runs/blobs/work/memory, native homes and generated assets. External configured paths survive physically, but lost configuration must be supplied again. Startup recreates fresh state and bundled assets, not historical records. |
| Home's `P` with defaults | [ensure_home_project](../../crates/spark-workspace/src/projects.rs) registers `$HOME`; default `P = H`. Deleting that physical root loses both project configuration and installation data. Preserve `H/definitions/{flows,roles,playbooks}` as active Home project definitions, never an installation-wide fallback and never a wholesale cleanup target. Home has no project `settings.toml`; installation configuration remains in `config/spark.toml`. |

No automatic purge, migration or compatibility import is part of rollout. Operators must deliberately preserve authored files/uncommitted work before resetting old private storage. Old formats are unsupported, consistent with [AGENTS.md](../../AGENTS.md).

## Alternatives considered

- **Keep existing private repositories.** Viable and cheaper, but leaves the subsystem-specific private stores and locks that this audit is meant to simplify. The earlier `smallest_sol` variant also proposed project settings and flow overrides; the operator rejected that settings layer in favor of project flow definitions. Its inventory omitted existing project model defaults in `project.toml`; their readers/writers must move with the registry into SQLite. Its verified worktree lead is addressed by resolving owning project, and its manifest-writer and memory-containment leads are incorporated above.
- **Consolidate private records while keeping current content roots.** Viable consolidation with less path churn, but leaves private working data in the checkout. The earlier `cleanest_opus` variant's deferral of a separate flow/node override layer is now consistent with the operator's decision; author model changes directly in project flows. Changing default Home or flattening definitions adds unrelated churn. Its staging promise conflicts with atomic project-file rename on another filesystem, so destination-local staging is retained. Its verified `run.log` lead justifies removal; its workflow-feed lead establishes supported API use despite no bundled frontend subscription. Reported operator-disk stale flows/empty directories remain unverified, not deletion targets.
- **Keep execution choices private and move only memory/triggers (`smallest_opus` and prior CR).** Keeping existing project model/execution defaults private is adopted, subject to the coordinator assumption below. The remaining narrower placement change loses because moving portable trigger definitions away from the project contradicts the accepted ownership boundary and leaving other private repositories fragmented misses consolidation. The verified dead registration directories and empty global logs deserve removal, while local generated working files are valuable data, not disposable cache. Stale definitions documentation and the Home overlap are explicitly addressed. Enabled-by-default trigger state remains a lifecycle bug under this alternative.

[VS Code workspace settings](https://code.visualstudio.com/docs/configure/settings) is the operator's analogy; its [ExtensionContext API](https://code.visualstudio.com/api/references/vscode-api#ExtensionContext) distinguishes workspace storage from global state. Adopt that ownership boundary, not its full hierarchy. [uv storage](https://docs.astral.sh/uv/reference/storage/) distinguishes disposable cache, persistent data and configuration. Adopt that distinction, not additional platform roots: Spark already has `SPARK_HOME`.

## Risks

- Broad coordinated change: settings, structured repositories, owning-project default lookup, filesystem paths, bundled prompts and UI cannot retain conflicting authorities. Land the paired reader/writer changes together per step below.
- SQLite becomes responsible for more private data. Preserve transactions, revision semantics and project deletion bookkeeping; never wrap database operations in long agent/network calls. This design makes no throughput claim.
- Profile names authored in project definitions need matching installation profiles; connection details, private project defaults and mission bindings are intentionally not portable. Errors must identify missing names/bindings instead of falling back.
- Containers/remote execution must expose work and memory correctly. Existing worktrees remain tied to their Git source, and no reset or relocation can repair them automatically.
- No migration means old private history is inaccessible. Historical material must be preserved deliberately before a reset; this implementation must not purge unknown files, active Home definitions or valuable work.
- Trigger file operations and SQLite cannot share a transaction. Fail inactive, recheck on dispatch, and distinguish confirmed removal from parse/I/O failure. Unobserved identical delete/recreate and external-side-effect exactly-once delivery are outside the guarantee stated above.
- File result metadata/prose are not a two-file transaction. Atomic per-file replacement and terminal materialization preserve the current mechanism; report incomplete materialization rather than adding a second prose authority.
